# اختبار الحمل والتحمل (V6 المرحلة 21)

أدوات تقيس قدرة التطبيق على خدمة 50,000 مستخدم مسجل: كم مستخدمًا متزامنًا يخدم الخادم بزمن استجابة جيد، وأين ينهار، وما الذي يجب إصلاحه أو ترقيته.

## قواعد الأمان (لا استثناء)
- **الاختبارات تلمس staging فقط، ولا تلمس الإنتاج أبدًا.**
  - كل سكربت يرفض العمل دون `APP_ENV=staging`.
  - يرفض أي رابط يطابق دومين الإنتاج (`DOMAIN`, `APP_DOMAIN`, `PUBLIC_URL`, `LEGACY_HOSTS` من `/opt/dzplay/dzplay/.env`) أو المنفذين 80/443.
  - يشترط أن يجيب الهدف `GET /healthz/env` بـ `{"env":"staging","loadtest":true}` (`lib/safety.py`).
- **الزرع لا يعمل إلا على قاعدة اسمها ينتهي بـ`_staging`** وعليها علامة `loadtest.staging`. العلامة لا تُوضع إلا في قاعدة فارغة.
- **`LOADTEST_MODE`:**
  - يُرفض تشغيل التطبيق به خارج `ENV=staging` (اختبار آلي في `tests/test_loadtest_mode.py`).
  - يحتاج `LOADTEST_TOKEN` من 32 حرفًا على الأقل.
  - ليس إعدادًا في اللوحة، ولا يظهر في `.env.example`.
  - ما يفعله، مع الرمز فقط:
    - عنوان IP اصطناعي لكل مستخدم افتراضي، فتُطبَّق حدود العنوان على كل مستخدم كما مع الهواتف الحقيقية؛
    - توكن تطبيق مؤقت بدل Key Attestation.
- **كل خدمة خارجية مزيفة** (`mocks/server.py`): لا بريد يُرسل، ولا رسالة تصل إلى البوت أو قناة التخزين.
  - Telegram (الصور من مجموعة ثابتة)؛
  - Bybit (بيانات ثابتة من ملف)؛
  - TronGrid/BSC (معاملات مؤكدة)؛
  - SMTP (صندوق محلي يعطي رمز التسجيل لسيناريو ز).
- الأسرار المولّدة والتوكنات والنتائج في `out/` و`results/`، خارج git.

## المكوّنات
| المسار | الدور |
|---|---|
| `staging/` | `docker-compose.yml` (مشروع `dzstaging`، المنفذ 8443 فقط)، `up.sh`، `down.sh` (يحذف كل البيانات)، `snapshot.sh save\|restore`، `local-2cpu.yml` (معالجان و~4.3 GB كخادم صغير)، `remote-generator.yml` |
| `seed/seed.py` | 50,000 مستخدم، 150 ألف فكرة، 600 ألف تعليق ورد، 2 مليون إعجاب، 30 ألف محادثة، إشعارات، 2,000 عضو، حركات ledger، سحوبات، جولة ظرف أحمر (≈ 7 دقائق) |
| `k6/` | نموذج سلوك المستخدم (`lib/session.js`، الأوزان في `profile.json`) والسيناريوهات (`main.js`) |
| `ws/wsflood.py` | السيناريو و: أقصى عدد ثابت من اتصالات WebSocket |
| `monitor/` | `collect.py` (المعالج والذاكرة والقرص وPostgreSQL وRedis وأزمنة التطبيق كل ثانيتين)، `k6sink.py` (السلاسل الزمنية من k6، ويوقف سيناريو ج عند نقطة الانهيار) |
| `report/build.py` | تقرير HTML عربي برسوم وجداول، و`summary.md`، ومقارنة قبل/بعد |
| `phase2/` | سكربتات الخادم: المواصفات، الصيانة، staging بإعدادات الإنتاج، الجدار الناري، ليلة الاختبار، الإيقاف الطارئ، فحص الإنتاج |

## السيناريوهات
| | الشكل | `--quick` | `--full` |
|---|---|---|---|
| أ | 100 مستخدم | 5 د | 11 د |
| ب | 500 ← 1,000 ← 2,500 | 18 د | 51 د |
| ج | +250 كل خطوة حتى أخطاء > 5 % أو p95 > 3 ث | حتى الانهيار | حتى الانهيار |
| د | 200 ← 3,000 خلال 60 ث ثم العودة | 9 د | 13 د |
| هـ | 1,000 مستخدم | 17 د | 62 د |
| و | WebSocket حتى الفشل (خطوات 1,000) | — | — |
| ز | تسجيل ودخول 30 ← 960 في الدقيقة مع 300 متصفح | 16 د | 28 د |
| S | 10 مستخدمين لدقيقة (فحص الأدوات) | 2 د | 2 د |

- كل مستخدم افتراضي هاتف حقيقي: 70 % أندرويد و30 % iPhone.
- يفتح التطبيق بنفس طلبات الواجهة (`/api/config`، `/api/me`، `/api/sync`، الأفكار)، ويبقي WebSocket مفتوحًا طوال الجلسة.
- ثم 4–14 إجراءً يفصل بينها 3–10 ثوانٍ:
  - تصفح وفتح أفكار؛
  - إعجاب وتعليق ورد؛
  - محادثة مع «يكتب…»؛
  - ملفات ومستخدمون وبحث وإشعارات والسوق؛
  - صفحات المال؛
  - ونادرًا: دخول، أو طلب عضوية، أو رمز سحب.
- 10 % من الفتحات «باردة» تحمّل ملفات التطبيق.

**الأهداف (SLO):**
- القراءة: p95 < 300 ms و p99 < 800 ms؛
- الكتابة: p95 < 600 ms؛
- الأخطاء < 1 % (429 تُحسب خطأً)؛
- معالج الخادم < 75 %؛
- بلا انقطاع WebSocket.

## التشغيل محليًا
```bash
cd dzplay
STAGING_IMAGE=… loadtest/staging/up.sh --local      # أو بلا STAGING_IMAGE: يبني الصورة من هذا المستودع
docker compose -p dzstaging -f loadtest/staging/docker-compose.yml exec -T -e APP_ENV=staging app python /app/loadtest/seed/seed.py
loadtest/staging/snapshot.sh save                     # مرة واحدة: نفس البيانات قبل كل قياس
loadtest/staging/snapshot.sh restore                  # قبل كل تشغيل مقارَن
APP_ENV=staging loadtest/run.sh --quick --label before A C F G
python3 loadtest/report/build.py loadtest/results/<قبل> loadtest/results/<بعد> --out compare.html
loadtest/staging/down.sh                              # يحذف staging كاملًا
```

**الإعدادات المقيسة:** تُمرَّر إلى staging من الصدفة:
- `WEB_CONCURRENCY`، `DB_POOL_SIZE`، `DB_MAX_OVERFLOW`، `THREADPOOL_SIZE`، `PASSWORD_HASH_CONCURRENCY`/`_QUEUE`/`_WAIT_SECONDS`، `WS_SESSION_RECHECK_SECONDS`؛
- `PG_MAX_CONNECTIONS`، `PG_SHARED_BUFFERS`، …

## النتائج (`results/<التشغيل>/<السيناريو>/`)
- `summary.json`: k6، من جهة المستخدم، مع كل مستوى على حدة.
- `timeseries.csv`: كل 10 ثوانٍ.
- `system.csv`: كل ثانيتين.
- `pg_top.csv`: أثقل 20 استعلامًا.
- `server_endpoints.json`: زمن التطبيق لكل نقطة.
- `break.json`: نقطة الانهيار.
- `wsflood.json`.
- `report.html` و`summary.md` في مجلد التشغيل.

**الإيقاف التلقائي:** يتوقف التشغيل فورًا إذا تجاوز القرص 85 %، أو توقفت حاوية من staging، أو سجّل التطبيق خطأً غير متوقع.

## على الخادم (المرحلة 2، بعد موافقة المالك فقط)
```bash
sudo loadtest/phase2/server-specs.sh > specs.txt          # قراءة فقط، بلا أسرار
sudo loadtest/phase2/night.sh --quick                      # الليلة كاملة بالترتيب، مع الأزمنة
sudo loadtest/phase2/abort.sh                              # إيقاف طارئ في أي لحظة: يعيد الإنتاج
```

**ترتيب `night.sh`:**
0. فحوص، وبناء صورة staging (الإنتاج ما زال يعمل).
1. نسخة احتياطية مشفّرة مع التحقق منها.
2. حدود اللوحة.
3. صفحة «صيانة مؤقتة»، وإيقاف الإنتاج.
4. staging بإعدادات الإنتاج.
5. الزرع.
6. السيناريوهات.
7. حفظ النتائج في `/var/backups/dzplay-loadtest`.
8. حذف staging.
9. إعادة الإنتاج، وفحصه (healthz + مسار الدخول)، وإزالة صفحة الصيانة.

أي فشل في أي خطوة يشغّل `abort.sh` تلقائيًا.

**مصدر الحمل:**
1. **خادم مولّد مؤقت بالساعة (مستحسن):**
   ```bash
   sudo GEN_HOST=ssh://root@<المولّد> GEN_IP=<المولّد> SERVER_IP=<الخادم> loadtest/phase2/night.sh --quick
   ```
   - k6 يعمل هناك عبر Docker فوق SSH.
   - منافذ staging (8443/8086/9000) مفتوحة لعنوانه فقط (`phase2/firewall.sh`).
2. **على نفس الخادم:** المولّد محدود بـ`K6_CPU_LIMIT` (افتراضيًا نواة واحدة). يأخذ جزءًا من معالج الخادم، فالأرقام أسوأ بقدر ذلك.
